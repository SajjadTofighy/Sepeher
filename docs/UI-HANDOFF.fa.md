# راهنمای تحویل رابط کاربری گشت نگهبانی

نسخه قرارداد: ۱۰ اکتبر ۲۰۲۶. این سند برای تیم مستقل UI است. منبع فیلدها و پاسخ‌ها `docs/openapi.json` و خروجی تولیدی `frontend/src/shared/api/schema.d.ts` است. DTO دستی تعریف نکنید؛ در `frontend/src/types.ts` فقط alias به schema بسازید. همه زمان‌های API را از UTC به Asia/Tehran تبدیل کنید و تاریخ روزانه را در رابط شمسی نشان دهید؛ تاریخ و ساعت ارسالی به API طبق ISO/OpenAPI باشد.

## ساختار و الگوی فنی

- قابلیت‌ها را زیر `frontend/src/features` بسازید؛ نقشه و لایه ایستگاه‌ها فقط در `features/command/OperationalMap.tsx` افزوده شوند. داده سرور با TanStack Query، بدون store سراسری دوم. پیام‌ها فارسی، اعداد با `fa()`، اجزای مشترک از `shared/ui`.
- برای هر درخواست میدانی guard، Bearer token و `X-Device-Id` را بفرستید. توکن وب فقط در حافظه بماند. از `/api/v1/auth/me` نقش‌ها و از `/api/v1/auth/permissions` مجوزها را بخوانید. فیلتر رابط صرفاً تجربه کاربری است؛ حوزه دسترسی را پاسخ سرور تعیین می‌کند.
- کلاینت میدانی OIDC باید `sepehr-field` با PKCE باشد. PIN عادی و PIN اضطرار فقط برای بازکردن قفل محلی در شیفت و تأیید آنلاین استفاده شوند؛ مقدار PIN در storage، analytics یا log نماند. توکن همچنان برای درخواست سرور لازم است و ذخیره رمزشده آن برای آفلاین، فاز ۴ است. قفل خودکار پس از عدم فعالیت و دکمه SOS قابل‌دسترس از صفحه قفل را در UI بسازید.
- `X-Classification` را در صفحه و چاپ نشان دهید و `X-Sepehr-Demo: 1` را با نوار هشدار دمو نمایش دهید. خروجی/چاپ را فقط از مسیرهای مجاز و همراه audit انجام دهید. نام، نوع، حساسیت یا مختصات ایستگاه را روی برگه فیزیکی تگ چاپ نکنید؛ فقط `tag-sheet.svg` یا code خنثی.
- خطاهای `detail.code` را جدا از متن HTTP مدیریت کنید: `guard_not_linked` به مدیر ارجاع، `device_required` به ثبت دستگاه، `device_revoked` به توقف عملیات، `scope_denied` به دسترسی نامجاز، `tag_replay` به اسکن تازه، `station_order_required` به صف ایستگاه بعدی. برای 409 وضعیت تازه را refetch و پیام سرور را نشان دهید؛ درخواست حساس را کورکورانه تکرار نکنید.

## جریان اجرایی فاز ۴ برای تیم UI

### نگهداری و پاک‌سازی

1. Service Worker فقط فایل‌های پوسته همان نسخه (HTML، JS، CSS، فونت) را در Cache Storage نگه دارد. هیچ URL زیر `/api/v1/`، هیچ پاسخ دارای `Authorization` و هیچ داده کاربر وارد Cache Storage نشود؛ پاسخ‌های API سربرگ `Cache-Control: no-store` دارند. هنگام نسخه جدید، کش پوسته قدیمی حذف شود.
2. داده میدانی را فقط در IndexedDB نگه دارید. از PIN نگهبان با PBKDF2-SHA-256، salt تصادفی ۱۶ بایتی ویژه همان دستگاه و `settings.offline_pbkdf2_iterations` کلید AES-GCM-256 غیرقابل‌استخراج بسازید. برای هر رکورد IV تصادفی ۱۲ بایتی تازه و AAD شامل `owner_sub`، `device_id`، نوع رکورد و نسخه schema به کار ببرید. salt، IV، نسخه و متن رمز در IDB می‌مانند؛ کلید مشتق‌شده فقط در حافظه باشد و با قفل اپ از دسترس خارج شود. PIN و متن باز در log، analytics، localStorage، sessionStorage و Cache Storage نمانند.
3. فقط صف امروز و فردای `GET /tour/queue`، ایستگاه‌های آشکارشده در `station_ids` همان پاسخ، گشت فعال خود نگهبان و تماس‌های همان محوطه از `GET /tour/zones` را دریافت کنید. ترتیب کامل مسیر تصادفی را از API مدیریتی یا cache مشترک وارد نکنید. هر بسته شیفت در `ends_at + settings.offline_shift_grace_minutes` منقضی و حذف شود؛ داده گشت بدون برنامه زمان پایان قابل اتکا ندارد و برای آن پیش‌بارگذاری آفلاین فعال نکنید.
4. refresh token کیکلاک فقط در همان IDB و با کلید مشتق‌شده از PIN رمز شود. در قفل اپ، کلید از حافظه کنار گذاشته شود. هنگام خروج، تغییر `sub`، دریافت `device_revoked` یا ابطال دستگاه در اعلان/پاسخ، همه پایگاه‌های IDB و کش‌های متعلق به اپ را پاک کنید و کلیدهای Web Crypto را رها کنید. خطای پاک‌سازی باید UI را در حالت قفل نگه دارد؛ داده حساب قبلی به حساب تازه منتقل نشود.
5. در ثبت دستگاه، `device_secret` را فقط یک‌بار برای `crypto.subtle.importKey` با `extractable=false` به کلید HMAC-SHA-256 تبدیل و CryptoKey را در IDB ذخیره کنید. کلید AES-GCM اضطرار را از همان راز دستگاه با مشتق‌سازی دارای برچسب مجزا بسازید و به‌صورت CryptoKey غیرقابل‌استخراج نگه دارید. متن `device_secret` پس از ثبت در storage یا log نماند. رکوردهای SOS، duress و man_down با کلید AES دستگاه رمز شوند تا دکمه SOS صفحه قفل به PIN وابسته نباشد؛ بقیه رکوردها با کلید PIN رمز شوند.

### قالب رکورد امضاشده و ارسال

`SignedQueueRecord` در OpenAPI شامل `kind`، `device_id`، `client_id`، `captured_at`، `previous_device_time`، `payload` و `signature` است. زمان‌ها رشته ISO دارای منطقه زمانی‌اند؛ همان رشته ارسالی امضا می‌شود. `previous_device_time` را همیشه بفرستید (برای رکورد نخست `null`) و زمان رکورد قبلی **در ترتیب ثبت محلی** را در آن بگذارید، حتی اگر ترتیب ارسال با اولویت عوض شد. برای هر `client_id`، بدنه و امضا در retry ثابت بمانند.

امضا HMAC-SHA-256 با کلید دستگاه روی UTF-8 JSON شیء رکورد **بدون** `signature` است: کلیدهای همه objectها به‌ترتیب واژه‌نامه‌ای، بدون فاصله، رشته‌های Unicode به‌صورت مستقیم، و `previous_device_time:null` در رکورد اول. خروجی امضا hex حروف کوچک باشد. سمت سرور همین قالب با `fieldstore.canonical` بررسی می‌شود. `payload` باید همان داده‌ای باشد که به endpoint می‌رود؛ مختصات را به شکل عدد JSON معمولی و بدون نمایش نمایی بفرستید. رکورد با امضای نامعتبر یا دستگاه باطل‌شده 403 و audit می‌گیرد.

تخلیه صف فقط با تأیید صریح ثبت توسط نگهبان آغاز شود؛ اولویت بالا پیش از اسکن و موقعیت است، اما ترتیب داخلی هر دسته پایدار بماند. برای 429/503/قطع شبکه backoff نمایی با jitter و سقف زمانی بگذارید؛ برای 401 عادی ابتدا refresh کنید. اگر refresh token منقضی است، رکوردهای غیراضطراری در صف بمانند و ورود دوباره با کیکلاک **همان `sub`** درخواست شود؛ 403 ناشی از `device_revoked` پاک‌سازی فوری می‌خواهد. 409/422 و `tag_replay` نیازمند بازبینی انسانی‌اند و نباید در حلقه retry شوند. `navigator.storage.persist()` را درخواست و کمبود فضا/رد درخواست را آشکار کنید. داده رمزگشایی‌شده فقط در مدت لازم در حافظه بماند.

پذیرش UI باید با قطع شبکه و توکن منقضی، دو حساب روی یک دستگاه، ابطال دستگاه با صف پر، اسکن پس از آستانه، پسروی ساعت، اولویت اضطرار و راه‌اندازی دوباره PWA روی گوشی سازمانی آزمایش شود. اجرای پس‌زمینه و ارسال خودکار در مرورگر تضمین نمی‌شود؛ وضعیت «در صف دستگاه / دریافت‌شده در سرور / رسید اپراتور» را جدا نمایش دهید.

## کنترل‌های تجربه کاربری و پذیرش

- وضعیت‌های draft/approved برنامه، queued/active/completed/excused دور، و planned/installed/damaged/revoked تگ را با متن و رنگ مستقل نشان دهید؛ رنگ تنها نشانه نباشد.
- بازدید ایستگاه دونفره بدون اسکن نفر دوم، dwell ناکافی یا وظیفه الزامی ناقص باید در UI توضیح داده شود؛ مرجع نهایی پاسخ API است.
- guard نباید در هیچ پاسخ یا cache رابط ترتیب کامل دور تصادفی را ببیند. با دو نقش guard و supervisor و دو پیمانکار این را آزمون کنید.
- تقویم: شیفت ۲۲:۰۰ تا ۰۶:۰۰، الگوی ۲۴ساعته، چرخه ۱ روز کار/۱ روز استراحت، وقفه، ۳۱ روز و مرز تهران را نمایش/ارسال آزمایش کنید.
- در وضعیت اضطرار، نوار واضح محوطه و دلیل را نشان دهید. `excused` را «موجه به‌علت وضعیت اضطرار» بنویسید و آن را خطای نگهبان نشمارید.
- حسگر واقعی، Wake Lock و قفل محلی تا زمان اجرای UI و آزمون روی گوشی سازمانی آماده بهره‌برداری نیستند. ادعای پایش قابل اتکا در پس‌زمینه PWA نکنید. ضبط و آپلود رسانه فاز ۵ روی گوشی و شبکه واقعی میدان آزموده نشده است.
- برای UI آزمون نقش/حوزه، وضعیت‌های 401/403/409/422، بازآوری صف پس از بازدید و عدم افشای seed/ترتیب کامل کافی است. قرارداد پس از هر تغییر API از OpenAPI دوباره تولید شود.
